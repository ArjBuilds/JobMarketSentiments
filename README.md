# JobMarketSentiments

**Shortlist** is a Streamlit dashboard where a student picks a company and sees, on one page, what it is like to work there and what it hires for: employee review sentiment, turnover, recent news coverage, the data-role skills Indian postings ask for, and the India data roles the company posted. It covers a curated library of 82 large global employers that also hire in India.

The analytics core is web data collection plus sentiment analysis with spaCy, VADER and TextBlob.

[PRD.md](PRD.md) is the specification: features, data sources, schema and build order.

## Real-time backend

This branch adds a backend beside the dashboard. Design, tradeoffs and full results are in [docs/BACKEND.md](docs/BACKEND.md); raw results and profiles are in [docs/benchmarks/](docs/benchmarks/). The Shortlist pipeline and its data are unchanged and don't depend on it.

- **Ingestion.** `backend.worker` polls the public Greenhouse Job Board API for the 15 boards in `backend/boards.csv` (no scraping) and matches skills against `data/skills.csv`. Responses are cached so a run can be replayed offline (`--source cache`). A labelled synthetic fixture covers tests and offline use (`--source fixture`).
- **Retries.** Network errors, 429 and 5xx are retried up to 5 attempts with capped exponential backoff and jitter, honouring `Retry-After`. Other 4xx responses fail at once.
- **Checkpoints and idempotent writes.** Each posting has a stable key, `greenhouse:<board>:<job id>`. A batch inserts only keys not already stored, and a board is checkpointed after its last batch, so a killed run resumes without losing or duplicating rows.
- **Kill/restart check.** `scripts/kill_restart_check.py` hard-kills the worker twice mid-board, restarts it, and compares the stored keys with an uninterrupted run.
- **Storage.** SQLite by default (no Docker). ClickHouse via Docker Compose (`BACKEND_STORE=clickhouse`). `backend.generate` writes seeded synthetic rows (default 10M) to separate, labelled tables.
- **Incremental aggregates.** Skill counts and posting volume by day are updated as rows arrive: by materialized views in ClickHouse, and in the same transaction as the postings in SQLite.
- **Live panel.** `backend.api` (FastAPI) streams the aggregates on `/ws/aggregates`. The "Live postings" page connects to it from the browser.

### Setup and run

Git Bash, from the repo root, with the venv active. Docker is needed only for ClickHouse.

```bash
python -m pip install -r requirements-backend.txt     # requirements.txt + fastapi, uvicorn, clickhouse-connect, numpy

python -m backend.worker                              # one pass over the 15 live boards, into data/backend.db (SQLite)
python scripts/kill_restart_check.py                  # kill/restart check on SQLite; exit code 0 = all checks pass

docker compose up -d --wait                           # ClickHouse 25.8 on 127.0.0.1:8123
BACKEND_STORE=clickhouse python -m backend.worker
python scripts/kill_restart_check.py --store clickhouse
python -m backend.generate --replace                  # 10M SYNTHETIC rows, seed 42 (--rows N, --seed S)

BACKEND_STORE=clickhouse uvicorn backend.api:app --port 8000
streamlit run app/app.py                              # open "Live postings" in the sidebar

python -m backend.bench                               # rewrites docs/benchmarks/ (needs ClickHouse and a cached live run)
pytest tests/test_backend.py                          # dedupe, checkpoint recovery, aggregate correctness
docker compose down -v                                # stop ClickHouse and delete its data
```

Settings are optional and listed in `.env.example`. No API key is needed for Greenhouse.

### Benchmark results

These figures come from one `python -m backend.bench` run on 2026-11-04. Hardware: 13th Gen Intel Core i7-13650HX (14 cores, 20 threads), 23.7 GB RAM, Windows (build 26300), Python 3.11.0, ClickHouse 25.8.33.6 in Docker with 11.5 GB. **The 10M-row dataset is synthetic**: generated by `backend.generate`, not real postings.

| Measure | Dataset | Result |
| --- | --- | --- |
| Skill matcher, before / after | 3,968 real Greenhouse postings, 3,732,056 tokens | 1.70 s / 0.17 s (10.0×, identical output) |
| Worker pass under cProfile, before / after | same | 6.2 s / 2.2 s |
| Worker ingest into ClickHouse (parse, skills, dedupe, insert) | 3,968 real postings | 1,785 rows/s |
| Synthetic insert | 10,000,000 rows | 422,757 rows/s |
| Synthetic generate + insert | 10,000,000 rows | 276,375 rows/s (36 s) |
| Live-panel snapshot query (p50 / p99) | 10,000,000 synthetic rows | 19.4 ms / 27.0 ms |
| Top 10 skills, 30 days: materialized view (p50 / p99) | same | 5.0 ms / 7.2 ms |
| Top 10 skills, 30 days: raw table (p50 / p99) | same | 9.3 ms / 13.5 ms |

Query times are client-side over HTTP, from 300 runs each. **Timings vary between runs** on this laptop CPU. On three separate runs the skill-matcher speedup measured 8.6×, 21.9× and 10.0×. A 10M-row synthetic insert ran at 131k rows/s while other work shared the machine, against 423k rows/s in the benchmark.

The speedup was done in Python. Profiling showed the skill matcher was the slowest function, so it now builds lookup windows only at tokens that can start a skill name. The original version is kept as `match_tokens_reference`, and the two are checked against each other on every benchmark run. **There is no Rust rewrite**: this machine has no Rust toolchain or MSVC linker.

### Known limitations

- **Single writer.** The duplicate check assumes one worker per database. Two workers writing the same board at once could double-count in the aggregates.
- **Edited postings** keep their first stored version. Closed postings are not removed.
- **No aggregate rebuild command.** The materialized views count only rows inserted after they exist.
- **ClickHouse is set up for local development only**: it listens on localhost and the default user has no password.
- **Skill matching** is a word list, so generic terms such as "Artificial Intelligence" are over-counted.
- **Not part of the library.** The 15 Greenhouse boards are global employers outside the 82-company library.
- **Project rule.** The project rules (CLAUDE.md, PRD.md) still name GNews as the only API. They would need updating before this branch is merged.

## Run it on your own computer

You need Python 3.11 and Git. No API key and no data download: the repo carries `data/demo.db`, the dashboard's data without the review text (about 1 MB).

On Windows, clone to a short path such as `C:\dev`, or turn on long paths (the Windows setting `LongPathsEnabled`). Under a long path like `C:\Users\<name>\Downloads\...`, installing spaCy fails because some of its file paths go over Windows' 260-character limit. The Windows commands below are for Git Bash.

```bash
mkdir -p /c/dev && cd /c/dev           # Windows; any folder is fine on macOS or Linux
git clone https://github.com/ArjBuilds/JobMarketSentiments.git
cd JobMarketSentiments
py -3.11 -m venv .venv                 # macOS/Linux: python3.11 -m venv .venv
source .venv/Scripts/activate          # macOS/Linux: source .venv/bin/activate
python -m pip install -r requirements.txt
streamlit run app/app.py               # opens http://localhost:8501
```

The sidebar starts collapsed: open it with › at the top left to switch pages or filter the companies table.

To update later, from the repo folder with the venv active:

```bash
git pull
python -m pip install -r requirements.txt
```

The app uses `data/demo.db` whenever `data/jmsa.db` is missing.

## Rebuilding the data

Only needed to rebuild the database from the sources, not to view the dashboard.

1. Install the spaCy model: `python -m spacy download en_core_web_sm`.
2. `cp .env.example .env`, then set `GNEWS_API_KEY` in `.env` (free key from https://gnews.io).
3. Download the Kaggle datasets into `data/raw/` under the names in [Get the data](#get-the-data).
4. Run the loaders and process steps in the order in [docs/dev/project_state.md](docs/dev/project_state.md) (also listed under [Build the database](#build-the-database)).
5. `python scripts/make_demo_db.py` refreshes the committed `data/demo.db`.

## How it works

Data collection is a batch pipeline, kept separate from the dashboard so a demo survives a dead or rate-limited API:

```
sources → ingest/   one loader per source, raw responses cached
        → process/  sentiment, skill extraction, turnover proxy
        → SQLite    data/jmsa.db
        → app/      Streamlit reads only from SQLite, never a live source
```

The one exception is the Live postings page. It reads the [real-time backend](#real-time-backend)'s WebSocket from the browser and shows "Not available" when the backend isn't running.

The ratings file was renamed by hand before the project began, and the three Naukri exports were merged by hand. The merge can't be reproduced: the exports re-downloaded in October 2026 appear to be a later version (about twice the rows, and 522 merged rows are in no export). The loaders check the columns they need: the ratings file needs `company_name, overall_rating, employer_size, industry, review_count`, and the postings file's columns are listed in PRD.md under "The postings snapshot".

Already in the repo: `data/companies.csv` (the library), `data/raw/company_aliases.csv` (name matching), `data/turnover.csv` (published attrition, hand-copied from company reports), and the editable keyword lists `data/themes.csv`, `data/data_role_keywords.csv`, `data/skills.csv`, `data/turnover_keywords.csv` and `data/news_queries.csv`.

## Build the database

Run these once, in this order, from the repo root with the venv active. Each step reads what the one before it wrote.

```bash
python -m jmsa.db init                    # empty database at data/jmsa.db
python -m ingest.load_companies           # the 82 companies
python -m ingest.load_glassdoor_ratings   # ratings for 66 of them
python -m ingest.load_glassdoor_reviews   # streams all_reviews.csv, writes the matched reviews (slow: 3.8 GB)
python -m ingest.load_reviews             # 1.8M matched reviews into the database
python -m process.review_sentiment        # VADER scores and per-company summaries
python -m process.sentiment_checks        # optional: method comparison and TextBlob agreement report
python -m ingest.load_jobs                # Naukri data-role listings
python -m process.skill_counts            # market-wide skill counts
python -m process.turnover_proxy          # review-based turnover proxy
python -m ingest.load_turnover            # published attrition (after the proxy, for its comparison)
python -m ingest.load_news                # GNews, one request per company (needs GNEWS_API_KEY)
python -m process.analysis               # report tables in docs/analysis/ (a few minutes: re-runs TextBlob on 50k)
```

Then `python scripts/make_demo_db.py` writes `data/demo.db` (the committed copy a fresh clone opens). Before a demo, commit, then freeze: `python scripts/freeze.py` writes docs/freeze.md (commit, row counts, source dates, input hashes).

`load_news` uses up to 82 of the free tier's 100 daily requests. If it exits with code 3, the daily quota is used up: rerun it after 00:00 UTC and it resumes where it stopped. It skips companies fetched in the last 24 hours.

Each loader writes a report to `data/raw/` (e.g. `naukri_match_report.txt`). To test a loader without touching `data/jmsa.db`, point `JMSA_DB_PATH` at a throwaway file.

## Run the dashboard

```bash
streamlit run app/app.py    # http://localhost:8501
```

Pages, in the sidebar (collapsed at first; open it with › at the top left): Explore (where the app opens: featured companies, recent articles by sentiment, and the company library, filtered from the sidebar), Company, Compare, Market skills, About the data, which lists every source with its dates and explains how each score is calculated, and, under Backend, Live postings (needs `uvicorn backend.api:app --port 8000` running). ## Data and ethics

Only sources whose terms permit this use: a Glassdoor company-ratings snapshot, a Glassdoor review-text snapshot, a Naukri snapshot of Indian data-science and analytics postings, the GNews API (free tier, non-commercial), and companies' own annual reports and filings. The real-time backend also reads the public Greenhouse Job Board API, which needs no key, and keeps no personal data from it. No scraping of LinkedIn or Glassdoor. No reviewer names or personal data are stored. Where a source has nothing for a company, the dashboard shows "not available" rather than an estimate. The review dataset is CC BY-NC-SA 4.0, and this project is non-commercial coursework.
